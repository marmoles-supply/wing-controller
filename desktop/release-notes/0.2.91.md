# WING CONTROLLER Desktop v0.2.91

Build: 20261005.13 (macOS Apple Silicon)
Date: 2026-10-05

## The Shoot card told the truth about everything except a toggle

A toggle step does not send the value stored on the step: it sends `-1` and the console flips the parameter, which is what
Maillot documents for any integer parameter that accepts only 0 or 1 ("By sending a -1 to an OSC Command with an integer
OSC Type Tag that can only accept values 0 or 1, the value of the parameter will toggle between 0 and 1"). The runtime has
done that since 0.2.63 - one packet, no read, no wait - but the card shown after a Test Action, both Shoot dialogs and the
session log printed `<address> <kind>=<stored value>`, so a toggle of `/ch/11/in/set/altsrc` reported `int=0` while
sending `-1`. The report was wrong, not the packet, and that is worse than no report at all: it sent an operator looking
for a fault in a step that was behaving correctly.

Every one of those places now prints what actually leaves, as `<address> toggle (-1)`.

## And the dead path that made this hard to see is gone

Two functions that read the live value and wrote the inverse - `execute_toggle_step_by_reading` and its inversion helper -
survived in the backend as dead code behind `#[allow(dead_code)]`, called only from tests, with a comment beside the real
executor still claiming that a toggle reads the leaf first. Nothing in the shipped path called them, but they made the tree
say two different things about the same step, and they cost real time in diagnosis. They and the tests that pinned them are
deleted. A toggle still refuses, with its reason, when the parameter is not an on/off one.

`Set` on a switch remains legitimate and unchanged: a step whose mode is `set` writes the value stored on it, which is
what makes "mute this channel" possible.
