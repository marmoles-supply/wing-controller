# WING CONTROLLER Desktop v0.2.56

Build: 20260927.1 (macOS Apple Silicon)
Date: 2026-09-27

Every dropdown in the app is the same control now — the closed box and the open list — and the desk
settled two protocol questions the documents left open. The live-safety items the master plan still
had open are closed in the backend, and the FX models' parameters reached the catalogue.

## One dropdown, drawn by the app

The native `<select>` was the last piece of the old look: WKWebView draws those itself and ignores
`appearance: none`, so the window showed macOS dropdowns beside the macro editor's own control. Every
plain `<select>` in both windows is now drawn by the same component the grouped picker uses — 45 of
48 in the workstation (the other three *are* the pickers) and both of the bridge's. The closed box is
the picker's field (white, sunken, the same bare chevron, the dark-theme variant) and the open list is
the picker's panel, with one row per option and a heading per `<optgroup>`.

The native element stays in the DOM and keeps its id, its value, its options and its events: anything
that reads or writes a select — a stored macro, a preset, a test — keeps working, and the drawn field
only ever writes back through `input` + `change`, the two events a real selection fires. Keyboard,
type-ahead, Home/End, Escape, click-outside and viewport placement are handled, and the panels stay
inside the window at every size tested down to 340×420.

The visual check is byte-level: screenshot crops of a drawn field against the picker's own field
(right edge with the chevron, the chevron itself, the left edge, both bevels) are identical in light,
dark and invalid states, in both windows. It found and fixed two shared-rule bugs that also affected
the picker: the dark theme tiled the chevron across the whole field, and the global button rule
centred the row labels.

## The desk settled `gate_ratio` and the gate's family

- **`/ch/N/gate/ratio` is offered now.** The extracted option list looked truncated (`…, 1:4, gate`),
  which is why the key stayed out rather than offering values the console might ignore. The desk says
  the list *is* those five rows and that the leaf takes strings: `1:5`, `1:10`, `1:100`, `GATE` and
  `EXP` are ignored, and an integer write is read as an index into the same five.
- **The gate node is a channel's alone** (re-checked live): `/aux/N/gate/{mdl,on,thr,range}`,
  `/bus/1/gate/on`, `/main/1/gate/on` and `/mtx/1/gate/on` answer nothing while `/aux/1/dyn/on` and
  `/ch/1/gate/mdl` (`GATE`) answer. The document lists aux gate leaves; the console has none, so
  refusing the key on an aux is the honest answer and it stays that way.

## Live safety and truth, in the backend

- **Live Safe Mode is enforced in Rust**, not only in the window: saving or importing a library or a
  show profile, starting the stream, a Shoot and every raw message are refused with a readable reason
  while it is on. The window pushes the *effective* lock, so a first connect with the preference on
  is not refused by itself.
- **A macro whose writes the console did not confirm is not a clean success**: the run reports
  `completed_unconfirmed` with the number of writes the console never confirmed, and only fully
  confirmed runs count as completed. Real failures behave exactly as before.
- **A Shoot can be cancelled.** The window gets `stop_test_action`; the run reports `cancelled`
  instead of success or failure, and PANIC STOP raises the same flag.
- **A recovery copy that could not be written back is not reported as restored** any more.

## No console identity in what the operator reads

The app is used with many different WING consoles, so no hint, label, dialog or build document names
the unit on the bench any more — not its discovery identity, its serial, its address or its firmware
build; "verified on hardware" is as specific as a hint gets. The evidence stays where it belongs, in
the code comments and the internal documents. A contract test walks every catalogue row of both
windows and fails on a `WING-` identity token, a dotted-quad address or a firmware build, so it cannot
creep back with the next batch.

## FX model parameters reached the catalogue

The parameters of the model loaded in an FX slot are catalogue targets now (`/fx/<slot>/<name>`,
gated by the model that slot reports), which closes the last item of the macro coverage plan. The
picker that groups them by model lands in the next build; until then they appear in the step list of
the `fx` category like any other key.
