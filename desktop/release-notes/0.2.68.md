# WING CONTROLLER Desktop v0.2.68

Build: 20261002.5 (macOS Apple Silicon)
Date: 2026-10-02

What the release itself carries, and the icon, which turned out to be the copy inside the image.

## The application's icon, everywhere

The installed copy was never the problem: the system's own icon lookup for it returns this application's
artwork. The copy **inside the disk image** was. `cp -R` onto a disk image copies the icon's flag but not the
picture in `Icon\r`'s resource fork, and the `xattr -cr` the build runs — needed so the signature verifies —
removes both. That copy therefore had an `Icon` file, the flag and no image, so an application run straight
from the mounted image showed macOS 26's dark tile until it was installed and unblocked.

The build now writes the icon into the image's copy and the ZIP's, and **refuses to produce a release** whose
copies do not carry the picture; the release verification checks it in both artefacts and asks the system what
it actually draws for them.

## The unlock helper speaks English

`Unblock WING CONTROLLER.command`, in the disk image, in the ZIP and in the instructions — the build's own
text is English, and a test refuses to let the old name come back into anything that ships.

## The changelog travels with the build

`CHANGELOG.md` — every release's entry, newest first — and this version's `RELEASE NOTES <version>.md` are
inside the disk image and the ZIP, beside the application. The release verification fails when either is
missing.

## And for every version from now on

`AGENTS.md` lists what each release ships and why the icon has bitten twice, and
`./scripts/release.sh <version>` is the one step that builds, writes the checksums and verifies the result —
so none of this depends on somebody remembering it.
