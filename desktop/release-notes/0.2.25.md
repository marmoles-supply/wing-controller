Date: 2026-09-21

## Clicking a field and typing works (root cause found and measured)

The operator's observation — *"it only works while I hold the click"* — was the key, and it
reproduced in the WKWebView harness (`scripts/dev-webkit-probe.swift --hold`):

```
button down  + type: insertText true
button up    + type: insertText false     <- the editing pipeline closes on release
```

With a temporary diagnostic inside a real instance of the packaged app (a `debug_note`
command writing to `/tmp`, removed again before this build) the state was measured directly:

- the window reports focused, `document.hasFocus()` is true, the field is the active element,
  the node is never replaced, the keydown arrives with `defaultPrevented=false`…
- and `document.execCommand("insertText")` still returns **false**: WebKit keeps the DOM focus
  but has its **editing pipeline closed**, so nothing the operator types lands.

What re-opens it, measured on a clicked-and-released field:

| action | insertText |
| --- | --- |
| `focus()` alone | false |
| `focus()` + `setSelectionRange` | **true** |
| `blur()` + `focus()` | **true** |

That also explains the two clues: holding the button worked because the mouse-down establishes
the selection, and right-click → Edit always worked because it calls `select()`.

The fix: `placeCaret(field)` in both windows re-applies the selection after focusing and, if
`document.queryCommandEnabled("insertText")` still says no, toggles the focus and puts the caret
back where the click was. It runs from `claimFieldFocus` on both `pointerdown` and `pointerup`.

Verified end to end on a real instance of the built app, with the diagnostics removed: click,
release, type — the character lands in the field.
