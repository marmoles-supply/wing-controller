# WING CONTROLLER Desktop v0.2.47

Build: 20260922.20 (macOS Apple Silicon)
Date: 2026-09-22

The station backup, fail-safe: saving always ends in a file and it says where; restoring reports what it has
applied.

## What was happening (both causes, found in the code)

1. **The native macOS panel could never answer.** The system panel is an AppKit *sheet*
   (`beginSheetModalForWindow:completionHandler:`) and its *completion handler* does not always arrive: if
   the window is not the active one, if the app is not in the foreground, or if a second panel is requested
   while one is open — macOS **queues** it instead of showing it— the plugin is left waiting **with no
   timeout anywhere in the stack** (neither in the plugin nor in `rfd`). Result: the `invoke` **neither
   resolved nor rejected**. No panel, no error, no file. That was the symptom.
2. **Version confusion.** `/Volumes/WING CONTROLLER` (without a suffix) is **0.2.41**: if the app is opened
   from that volume (the one with the "good" name), the export is still the `data:` URL download, which in
   a packaged app **writes nothing**. The same thing explains why the restore had no file to open.

## What it does now

- The panel is requested with the plugin's **callback API** (non-blocking) and with a **25 s watchdog**: if
  it does not answer, it is given up on and we carry on.
- **A single panel in flight**: a second attempt is rejected immediately instead of being queued (which is
  what left the first one hanging).
- **Plan B that guarantees the file**: if the panel fails, does not answer, or the operator cancels, the
  backup is written to the **backups folder** (`Documents/WING CONTROLLER backups` by default, changeable
  with **Folder…**) and the notice says so, with the reason.
- **Ask where to save** (ticked by default) keeps the dialog when you want it; unticked, the file lands
  straight in the folder with the show name, with no dialog to close. During a show that is what you want.
- The final notice **always says the path**, offers **Show in Finder** and the log records every step;
  there is also a record in `~/Library/Application Support/Wing Controller Desktop/logs/backup.log`.
- **The tab says which build is running** (`Running WING CONTROLLER 0.2.47 (build …)`) and the session log
  starts with `app_start version=… build=…`. No more losing a night to version confusion.
- **The whole export handler runs inside a `try`**: building the payload, saving and the notice. It can no
  longer die in an uncaught promise with no dialog and no trace.
- **Restoring reports what it has restored**: when the window comes back, a notice says the file and the
  sections applied with their counts. And the file picker is the webview's own (native, with no plugin in
  between), which is the path that has always worked. Backend errors are no longer lost as `undefined` in
  the message.

## What to try

1. **Open the app from THIS DMG** (`/Volumes/WING CONTROLLER 6` or whatever it mounts as) and, before
   anything else, look in **Properties → Profiles & Backup** at the line that says
   `Running WING CONTROLLER 0.2.47 (build …)`. If it does not say 0.2.47 there, you are opening another
   copy: eject the old DMGs (`/Volumes/WING CONTROLLER` is 0.2.41).
2. **Export**: type a show name, tick Macros and Meters, press **Export Station Backup**. The Save panel
   must open (in front of the window) or, if not, the notice must appear saying it has been saved in the
   backups folder **with the path**. Check that the file is there (**Show in Finder** button). Repeat with
   **Ask where to save** unticked: it must land straight in the folder.
3. **Restore**: **Restore Station Backup**, choose the file, leave only the sections you want ticked and
   accept. When it comes back, the window must **tell you what it has restored**.
4. If something goes wrong: look at `~/Library/Application Support/Wing Controller Desktop/logs/backup.log`
   (it says the version, every step and the reason for any failure) and send it to me.
