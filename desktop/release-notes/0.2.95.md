# WING CONTROLLER Desktop v0.2.95

Build: 20261008.2 (macOS Apple Silicon)
Date: 2026-10-08

## The cue row is a table now

You reported it with a screenshot: *"las celdas de la tabla deberían ser fijas. está todo desordenado y feo"*.
It was, and it was four separate mistakes rather than one. A rendered contract now measures every one of them.

**The fields started at a different x on every row.** The line of fields was right-aligned with
`margin-left: auto`, so where it began was the row's right edge minus that row's own width - and the macro's
name and the repeat value are never the same twice. It is now a grid with a fixed template, so a column is a
column.

**A row missing a field moved every field after it.** A grid fills its tracks in order, so a cue with no macro
and no repeat pushed its duration field into the first track, where it sat at the row's left edge. Every field
now names its own track, so an absent one leaves an EMPTY TRACK instead of moving its neighbours.

**A cue with no number moved the time beside it.** The number badge was drawn only when a cue had a number, and
the time is a flex item, so on the other rows the time became the first cell and shifted left. The row now has a
slot that exists on every row and a badge that exists only where there is a number - a track and a value are not
the same thing.

**And every field in the row was drawn as a raised face.** The kit's rule is that a number the operator reads
sits in a WELL, and a well is the same bevel pair, reversed. The row had it the other way round, and the fields
that are always on screen - the number, the name, the section, the time, the macro, the repeat, the duration -
had no border of their own at all and took the browser's, which is raised. All 35 fields are now wells, in the
kit's own field token and its number type.

## Why this took a measurement rather than an eye

The window looked wrong and the DOM was always correct, so no test that reads structure could see it. Two new
contracts measure what is RENDERED instead:

- every column's cells must share their x, across every row that has that cell;
- every field the row draws must be a well - dark edge on the top and left, light on the bottom and right - and
  must be set in the kit's number type.

**The second one found the fourth mistake on its first run**, on the fields I was not looking at. The first one
found the second and third. Neither could have been found by reading the CSS, because the cause was a property
two files shared: the module draws the row and the window lays out the fields inside it.

And the guard that was meant to protect this row said so itself, once it was asked: **a source guard can say who
declares a class; it cannot say that a declaration in one file and a declaration in another cancel each other
out.**
