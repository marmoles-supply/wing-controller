# WING CONTROLLER Desktop v0.2.87

Build: 20261005.9 (macOS Apple Silicon)
Date: 2026-10-05

## The cue-only choice can finally be made, and builds keep one signing identity

**"Only a cue fires it" is now reachable.** The macro editor's empty trigger entry left a seeded channel id
behind - the code did it deliberately, because the completeness rule refuses a trigger with no id - so
choosing it produced a trigger that was *half set*: an empty source beside a filled id. The macro could not
be enabled as cue-only at all, and the only way through was the one an operator found for himself: give it
a trigger, enable it, and then clear the trigger while it was already enabled. Choosing the empty entry now
empties the id and the watch parameter as well, so the state the choice names is the state the window
leaves. The seeding is untouched for real sources, and a half-set trigger is still refused and still says
what to do.

**A build keeps one signing identity, so a grant can outlive it.** The application was signed ad-hoc, which
made every build a new code identity to macOS: the microphone grant is stored against that identity, so a
fresh build no longer matched the grant - and because the stored row still said "granted", macOS never
asked again. The result was an application that was told there were no audio inputs at all, with no dialog
and no error. Builds are now signed with one stable identity, created by a script in this repository, and
the build **fails** rather than falling back to ad-hoc, because a silent fallback would recreate exactly
this bug while looking healthy.

**One more time, and then not again.** A grant recorded against an ad-hoc build does not apply to the
first identity-signed build, because to macOS that build is still a new code identity. After installing
this version, remove and re-allow WING CONTROLLER in System Settings > Privacy & Security > Microphone,
then press Refresh. From that grant onwards the stored requirement names the certificate rather than a
per-build hash, and later builds keep it. What was measured here is the requirement: two consecutive
releases signed with this identity carry byte-identical requirements and each satisfies the other, where
the two ad-hoc releases carried different ones. What has **not** been measured is a live grant surviving a
real install-and-update, which needs a person at the dialog twice - so this note does not claim it.
