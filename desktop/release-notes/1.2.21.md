# WING CONTROLLER Desktop v1.2.21

Build: 20260921.8 (macOS Apple Silicon)
Date: 2026-09-21

## A left click on a field starts editing again

The app's text boxes looked editable but refused the first left click; the only
route that worked was right-click → Edit. Measured in the real engine (WKWebView,
with the new `scripts/dev-webkit-probe.swift`, since Chrome does not reproduce
WebKit's behaviour):

- A field can hold the DOM focus while the engine refuses every edit. While the
  window is not focused, typing does nothing and even
  `document.execCommand("insertText")` returns false; the moment the window is
  key, the very same click types fine. That is the "looks editable, does not let
  me type" symptom.
- macOS does not deliver the click that activates an inactive window to the web
  content unless `acceptFirstMouse` is on (Tauri's default is off). A right-click
  does open its menu on an inactive window, which is exactly why the right-click →
  Edit route worked while a direct click did not.

Both windows now set `acceptFirstMouse` and, on the first click over a typeable
control, claim the window (`setFocus`) and focus the field — only when
`document.hasFocus()` is false, so the native caret placement is untouched in the
normal case.

This also corrects the record for 1.2.20: the `user-select` rule added there was
not the cause. A/B measured in WKWebView, the macro fields already computed
`user-select: text` with and without it. The rule stays as a guard against blocks
that set `user-select: none`, with an honest comment.

## HUD alerts: colour flash instead of the window blinking

`hudStrobe`/`hudPulse` animated `opacity` from 1 down to 0.15 on the alert card
and, in fullscreen, on the overlay itself: the alert — and with it the whole
window — appeared and disappeared. The flash is now colour, never opacity:

- the card's ring and the title bar pulse between the urgency colour and its
  bright variant;
- in fullscreen an inset shadow washes the screen over the overlay background, so
  it also works with a custom colour (whose background is set with `!important`);
- the alert text stays opaque and legible (white message in fullscreen; with a
  custom accent the title bar is darkened and the title kept white).

## HUD alerts appear fully formed

The card slid in with `hudSlideIn` and the toast with `hudToastIn`. Both are gone,
along with the card's `transform` transition: a fade/translate on appearance is
what looked glitchy and left the alert translucent just when it had to be read.

## Inspector and hover box: every control answers

The hint map grew from 77 to 220 entries (library toolbar, macro editor, HUD alert
fields and defaults, meters, OSC monitor, network, matrix dialog, deletion dialog,
diagnostics) and the fallback that covers the rest was rewritten: it reads the real
label (including `<label>Text <input/></label>`), says what the control is and what
it currently reads ("Dropdown with 5 options, currently set to …", "Check box,
currently ON [X]", "Slider from 150 to 2500, currently 330"), names the block it
belongs to instead of the old "WING CONTROL" placeholder, and humanises the id when
there is no label at all. The Meter Bridge got the same fallback, so its ScreenTips
are no longer a flat "WING meter bridge control."

## Verification

`./scripts/verify-all.sh`: 20 checks — TypeScript, both windows' script syntax,
every Node test (five of them driving the real UI in Chrome), the strict Maillot
path audit (0 unknown addresses) and `cargo test --workspace`.

New in this release: `scripts/test-desktop-hud-flash-browser.mjs` (36 display ×
urgency × flash combinations in both windows, plus a custom colour in fullscreen),
`scripts/test-desktop-inspector-hints-browser.mjs` (own entry beats the container,
the fallback, the settings dialog, 79 main-window controls and 12 + 23 bridge
controls), `scripts/test-desktop-field-focus-browser.mjs` (a cold first click
claims the window and focuses the field; a warm one does not interfere) and
`scripts/dev-webkit-probe.swift` (drives the real UI inside WKWebView to settle
Chrome-versus-WebKit differences).

## Known state

The click fix is verified in the engine and in Chrome, but the end-to-end
verification in this packaged build is the operator's first left click on a text
box: the caret must appear and typing must land immediately. If it still does not,
the useful datum is whether a second consecutive click works.
