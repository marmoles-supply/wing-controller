# WING CONTROLLER Desktop v0.2.98

Build: 20261010.2 (macOS Apple Silicon)
Date: 2026-10-10

## Four faults the gate had been red on, and a gate that closes green

Since 9 October the project's own verification gate had been reporting four failing browser suites. They are fixed
here, and with them the gate: **`ALL GREEN · 75 checks passed`** — the first release in months whose gate closed green
before it was cut. Three of the four were faults in the application.

**A dropdown could open off the edge of the window.** When the button that opens one had been scrolled out of sight —
measured: at a 420 x 720 window scrolled down, the picker's own button sat at 746…770, below the bottom of the window,
and its panel opened upwards from it at 558…744, hanging past the edge — the last entries of the list could not be
reached at all. The two rules that place a menu each *choose a side*, and neither could help a button that is itself
off screen. Every menu — the grouped picker, its submenus and the flat lists — now ends by being held inside the
window: one that still fits is shifted along the edge it already opened against (so which side it opens on is still the
stylesheet's decision), and one taller than the window is capped and scrolls, because every entry being reachable is
the whole point of a list.

**The Meter Bridge's dropdown fields were a drifted copy of the workstation's.** The same control is declared in both
windows, and the two copies had parted: the bridge's field set its own text size (11 px, where the workstation takes
the shared design kit's 9.3 px), hard-coded border facets that were the kit's own colour tokens written out by hand,
and a dark-theme border pair the workstation does not use; its panel's drop shadow was the light one in **both**
themes, so the dark theme never got the shadow the workstation has; and its rows set their own 11 px against the
workstation's 9.3 px. All of it now comes from the same source as the workstation's, and the bridge's buttons wear the
same dark bevel as the workstation's instead of one field restating it. The bridge's dropdowns read the same as the
workstation's because they are the same control again.

**And the test that measures them was not measuring the theme it assumed.** Each window opened from a local file keeps
its own storage on this platform, so the two windows can sit in different themes and each keeps whichever one was last
used. The suite pinned light-theme colours and then compared a dark bridge against a light workstation, reporting the
difference as a layout fault. It now pins the theme in both windows and checks **both themes** — which is where this
family of fault hides, and the dark theme of that control had never been measured at all.

**The timecode window's cue list could be squeezed shorter than one cue.** Measured at 420 x 200 — the box a window
manager that refuses to resize leaves — the list was 21.5 px tall against a 22 px row, so scrolling to the end showed
the last cue hanging out of the top of its own box: the window said it scrolled and the last cue could not be read.
The list is now never shorter than one row, and that floor is **measured from the row itself** rather than written
down twice, so it cannot drift from the row it is made of. With the list open in a short window the spacing between
the clock's lines tightens to make room; the folded clock — the shape that window opens in — is untouched, pixel for
pixel.

One more, smaller: the contract that a disabled button looks disabled demanded two exact grey values, and the
workstation had already replaced those with the shared kit's own dim colour. It now reads the colour from the page's
own token, so a token change can never leave the test demanding a colour the application no longer has anywhere.

## What was measured, and what was not

- Every geometry claim above is a number taken from the rendered windows in the project's own headless browser, and
  each of the four faults was put back by hand afterwards to confirm the contract fails and names it.
- The one colour claim — the bridge's dark theme — is a measurement of **both** windows in the same theme, taken
  after pinning it, which is what the suite had never done.
- The recorded images of the windows were re-shot and looked at (the bridge's dropdown fields and their dark bevel);
  nothing else moved.
- **Not measured**: your screen. The packaged window cannot be driven from a test, so what is claimed here is what
  the files this build ships do under the same engine — the final word is yours, looking at it.
- **Needs the desk, and not claimed here**: whether a console quantises a float write, which decides whether a fade
  that lands on a coarse parameter can be reported as "not applied"; and whether a microphone grant survives a real
  install-and-update. Both are listed, with their evidence, in `docs/MACRO_FADE_AUDIT_2026-10-09.md` and
  `AGENTS.md`.

## What this build contains besides the four fixes

The click rule in the cues window and the macro editor's fade work — including a fade that starts where the parameter
is and moves it by an amount, and fade endpoints that belong to their own parameter rather than being levels in dB —
shipped in **0.2.97**, which is already out. This build adds the four fixes above on top of exactly that tree, so
nothing from 0.2.97 is missing here and nothing here changes what it did.
