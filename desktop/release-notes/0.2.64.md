# WING CONTROLLER Desktop v0.2.64

Build: 20261002.1 (macOS Apple Silicon)
Date: 2026-10-02

Three things, all of them about the application being trustworthy at a desk.

## Nothing is sent to a console the application is not connected to

Every console write in the app goes through one gate: a **live session** first, then Live Safe Mode's own
rule. Until now that gate only knew about Live Safe Mode, so **Test Action** and the raw send reached a
console while the window said "disconnected" — the operator reads the badge and the desk does what it is
told. With no session the commands now refuse, name the state they saw, and send nothing:

> Not connected (idle): testing a step on the console needs a live session, and nothing was sent.

Connect first, then test. That is the point: nothing in this application writes to a console it is not
talking to.

## Fire a whole macro from its row

**Right-click a macro row → Fire Macro (run all its steps).** It runs the macro's enabled steps through the
same dispatcher a trigger uses, so what you fire is what the show will fire, and the run reports what each
step did (`confirmed`, `unconfirmed`, `interrupted`). Test Action proves one step; this proves the **list**,
which is what has to be trusted before a show.

It is offered before the "unsaved changes" question, because firing does not touch the editor — and nobody
should have to discard work to prove a list. The row's other actions still load the macro and therefore
still ask.

## The icon keeps its image

The Dock had gone back to the dark system tile. macOS 26 forces an app's legacy `.icns` into its squircle;
the way out is a *custom* icon: an `Icon\r` marker plus the kHasCustomIcon bit, with the artwork in that
file's resource fork.

On this machine `NSWorkspace -setIcon:forFile:options:` sets the flag and creates the marker but writes
**no image**, so Finder fell back to the bundle's icon and the tile came back — while the project's own
check reported "custom icon present", because it only looked at the flag. `scripts/write-custom-icon.py`
now writes the resource fork itself, the check demands the image rather than the flag, `verify-install.sh`
fails the release if an installed copy loses it, and a test round-trips the format (which was wrong the
first time: the resource map's reserved bytes).

## And an instrument for the next time a macro does not fire

`LIVE_WING_MACRO_REPRO=1` (hardware-gated) compiles a macro through the application's own library path,
prints the meter descriptor it asks the console for and the trigger it builds, subscribes exactly as the
stream does and reports the values against the threshold. It is how "why doesn't my macro fire?" was
answered on the real console — the macro was listening, the channel had no signal above its threshold —
and it should never again take an hour to find that out.
