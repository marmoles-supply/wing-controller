## The click rule, fixed where it was actually broken

You said it plainly: *"lo de los clicks aún no funciona en todas partes. por ejemplo, la ventana de cues"*. 0.2.96
brought the rule to every window, and in the cues window it still did nothing. Two separate causes, and neither was
the one the last build had fixed — both were found by driving the **real engine** (WKWebView, the one the application
runs) with a real click and a real keystroke, because Chrome's own behaviour had been hiding them.

**The list repainted itself under the click, and the repaint took the field with it.** A click on a cue's field
selects that row, selecting redraws the list, and the redraw replaced the very box the caret was in: measured, the
window's focused element was `body` after the click and the next key you pressed changed nothing at all — the field
was gone. It does not happen any more: the list puts that field back where it was, with the selection it had, and a
click inside the row that is already selected no longer redraws anything, because nothing about the selection
changed.

**And the rule was applied a moment too early — or a moment too late, depending on how you look at it.** The engine
places the caret itself as the *default action* of your press, and a default action runs after every listener, so
whatever a listener set was collapsed again straight away. Measured in the real engine: with the whole value selected
on the way down, typing `42` over `-18` still produced `-1842`. Doing it in a `click` handler produced `-1842` too.
And the frame the last build used to put it back — a `requestAnimationFrame` — **does not fire at all while the
application is not the front application**, which is exactly the window you are looking at, so the rule ran in the
test suite and never ran in the app. Now the press that the rule owns does not get to place a caret: the engine's own
placement is cancelled and the selection is set right there. Measured after the change, same tool, same field:
one click then `42` gives `42`; two clicks give `01:00:10:0042` (the caret at the end, so typing appends); a third
click inside the text gives `4201:00:10:00` (the engine's own caret, where you pointed).

One more thing had to be true for the second click to behave like a second click: the press count is now kept
against the field's *address* rather than against the box itself. A row that rebuilt itself between two clicks
produced a new box, and the counter treated your second click as a first one — so it selected everything again
instead of leaving the caret at the end.

## Also in this build

- **The macro editor's fade work**, which was already in the tree when this build was cut: a fade can now start
  where the parameter is and move it by an amount, and a fade endpoint is a value of its own parameter rather than a
  level in dB — which is what made fades work on faders and fail on EQ bands, pans and release times. Its own record,
  with the measurements and the open items, is in `CHANGELOG.md` and `docs/MACRO_FADE_AUDIT_2026-10-09.md`.

## What was measured, and what was not

- Every claim above is a number from the real engine, taken through `scripts/dev-webkit-probe.swift`'s own event
  path — the probe this project already had, extended in this session with a stub loader, a click counter and a hit
  test, and left in place for the next time Chrome and the application disagree.
- The cues window's contract now drives a **real mouse click and a real keystroke on a cue's own field**, on a row
  that is not already selected — the case that repaints the list — and asserts the field stays focused, the whole
  value is selected, one key replaces it, and a second click appends. Three mutations put each half of the defect
  back and the contract failed naming it every time.
- The `./scripts/verify-all.sh --quick` gate is green, and the cue, caret and LTC browser suites pass in full. The
  **full gate** still reports the four browser suites that were already red before any of this work (field
  validation's 420 px popover, the meter bank selector, the meter bridge's dim colour and the Timecode clock's
  layout); they are not this build's and each was re-run against an earlier revision, where it fails identically.
- **Not measured**: your screen. The packaged window cannot be driven from a test, so what is claimed here is what
  the files this build ships do under the same engine — and the final word is yours, looking at it.
