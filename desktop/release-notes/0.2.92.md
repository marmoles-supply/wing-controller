# WING CONTROLLER Desktop v0.2.92

Build: 20261007.1 (macOS Apple Silicon)
Date: 2026-10-07

## A wrong frame rate stops being quiet

LTC carries no frame rate: the rate is **declared**, and until now a declaration that did not match the incoming signal
was silent — the clock simply decoded nothing while the page said "Listening at 30 fps" over a 25 fps source.

The input now **measures the signal's own bit timing** as it decodes. The measurement is exact rather than approximate
(a one's two halves are two intervals that sum to one bit period) and it escapes the trap a count would fall into: a
count-derived estimate is biased towards the declaration, because the decoder only accepts numbers valid at the declared
rate, so a 30 fps signal read as 25 decodes 25 numbers a second and "confirms" itself. The bit period cannot: a real 25
read as 30 measures 25.

When the two disagree by more than 2 % the window says so, naming both numbers — *"listening at 30 fps, but the signal's
own bit timing is 25.0 fps"* — and says what to change. It never says "detected": what is measured is the signal's
playback speed at the sample rate the device reports, so varispeed and pull-up move it exactly as another frame rate
would. And 29.97 against 30 is never reported, because 0.1 % apart is what a boundary looks like and only the drop-frame
bit can tell those two apart.

## A stream that goes quiet stops pretending it is listening

A device can die without an error callback: the stream stays open, the system still reports it, and nothing arrives. The
page went on saying "Listening" for ever over a signal that had stopped.

The input now watches the **age of the data**. A stream that has decoded and then gone quiet for a second says so, with
the seconds named, and it is reopened **once** — bounded, with a twenty-second cooldown, logged with its wall-clock time,
and never over a stream that has never decoded at all, because that fault is the rate or the channel and reopening it
would replace the diagnosis with a retry.

## A macro that changed is a note, not a gate

A cue records a **content hash** of the macro it names, and when the library's copy no longer matches, the LTC window's
inspector says so: *"This macro has changed since this cue named it. The cue still fires the macro it names…"*. The cue
keeps firing exactly what it names — it is information, never a refusal, and it is printed in plain text with no mark, so
it cannot be mistaken for one more broken link. A cue that never recorded a hash is not judged at all.

## A list with two stored frame rates saves again

A cue is stamped with the rate of the source at the moment it is added, so changing the input's rate between two adds
produced a list the save **refused**: "the cue list mixes frame rates". The refusal is gone. Stored rates are a record of
what each cue was written against; the format the source is speaking now is what gives a cue its meaning, and a list that
was previously unsaveable saves and fires.

## The LTC window says more, and lies less

- **Used by N cues.** A macro shared between cues says how many of this list name it and **which** they are, named as the
  rows name them; a macro only one cue names says so, which is what makes it safe to edit; a cue that names nothing says
  nothing. A row carries a quiet `×N` when a macro is shared.
- **Sections.** A cue belongs to a section: a free name, typed on its row, with the names the list already carries
  offered so one section cannot acquire two spellings. Nothing about firing changes with it.
- **The next cue says what it is waiting for** — `next LTC` when the incoming timecode will cross it, `next on Go` when
  the operator's Go fires it — and only the clock gets a countdown, because nothing is counting down to a cue that waits
  for a person.
- **Bulk shift.** A selection can be moved by a signed number of frames, previewed before it applies, refused rather than
  wrapped at `00:00:00:00`, and taken back with **one** Undo. The global offset is not touched by it.
- **Enter** on a row appends a cue at the end, beside the existing Capture in the footer.
- Three defects are fixed that made rows describe a show that was not the one being run: the chain now reads the live
  safety state instead of assuming firing is allowed, a missing health report shows as **unknown** rather than as "fine",
  and saving from this window no longer reverts an offset that was edited in Settings.

## Behind the scenes

The verification gate can now report a wedged browser instead of hanging on it: every browser command has a deadline and
says what it asked for, how long it waited and whether the browser is still answering, so a machine that stops responding
produces a diagnosis rather than a run that never ends.
