# WING CONTROLLER Desktop v1.2.18

Build: 20260921.5 (macOS Apple Silicon)
Date: 2026-09-21

## New action mode: Toggle (flip on/off)

Actions can now alternate a binary parameter instead of forcing a fixed value.
Useful for a footswitch-style macro, an alternate source flip, a phantom swap, or
any cue that should reverse whatever the console is doing right now.

Choose **Toggle (flip on/off)** as the action mode. The value field disappears,
because the value is not authored: the app reads the current state from the console
and sends the opposite one.

How it works, and why it is built this way:

- The action reads the parameter with an argument-less OSC read **on its own
  socket**, at the moment the step runs. Verified on hardware that the console
  answers the requesting socket even while the streaming window holds the `/*S`
  subscription, so the value is authoritative and not a cached guess.
- The reply is parsed with the same rule as everywhere else in the app: a leaf read
  answers `,sff`/`,sfi` (ascii, raw, value) and the real value is the last argument.
- The inverse is sent as an integer `0` or `1`.

**It fails closed.** If the console does not answer within 400 ms, or answers with
something that is not a clean on/off value, **nothing is sent** and the step reports
an error explaining what it saw. Guessing the state would make the result
unpredictable, which is worse than doing nothing in a live show.

**It is not idempotent.** Every trigger flips the state, so a duplicated or repeated
trigger flips it back. Overlap policy `drop` limits duplicates coming from the macro
itself, but a manual re-trigger always changes the result. Use `Set` for anything
that must land in a known state.

Validation (`Verify`/preflight) accepts a toggle only on an on/off parameter such as
a mute, phantom, phase, alt source, send on/off, insert or user button. A toggle on
a fader or a filter frequency is rejected with a clear message. A raw custom address
is allowed, with a note that only an exact `0` or `1` will be inverted.

Cost: one extra round trip, about 1 ms on a wired LAN, plus the normal 17 ms OSC
send pacing.

## Validated on hardware, including the writes

Against a real WING Rack, verified on hardware, on a console that was not in a show, with
every touched value read beforehand and restored afterwards:

- **Toggle alternation, both directions.** `/ch/36/mute` read `0`, the step computed
  `1`, the write was applied and read back as `1`; the second round read `1`,
  computed `0`, applied it and read back `0`. The mute was then restored to `0`.
- **A path that could not be written before now writes.** `/ch/1/eq/lg`, resolved
  from the new `eq_low_gain` parameter, read `0.0`, accepted `-3.0` and read back
  `-3.0`, then was restored to `0.0`.
- **The original defect is now proven, not inferred.** Writing `-50.0` to the
  footnote-suffixed `/ch/36/gate/thr23` left the threshold at `-40.0`, unchanged,
  while writing `-50.0` to the corrected `/ch/36/gate/thr` read back `-50.0`. That
  is exactly the silent no-op: the console ignored the write. The threshold was
  restored to `-40.0`.

State after the run: mute `0`, EQ low shelf `0.0`, gate threshold `-40.0`, the same
values the console had before.

Still not covered by an automated pass: a full show workflow driving a toggle from a
meter or timecode trigger inside the packaged app, and the fail-closed path when the
console stops answering mid-run. Those need an operator rehearsing.
