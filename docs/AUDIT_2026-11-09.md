# Public release audit — 9 November 2026

This is a bounded source, dependency and packaging review for Desktop 0.3.0,
not certification for a show. **MEASURED** means a command/test was run here;
**DOCUMENTED** means source or an external authority establishes it; **INFERRED**
marks a consequence needing measurement; **COULD NOT ESTABLISH** names a limit.
See the [roadmap](ROADMAP.md) for tasks and acceptance criteria.

## Scope and architecture

Review covered the Rust desktop backend, its shared runtime/transport crates,
the local workstation UI, persistence/restore, timecode lifecycle, WING protocol
contracts, release packaging and contributor workflow. The parked mobile tree
was inventoried but neither built nor upgraded. See [architecture](ARCHITECTURE.md).

## Storage: implemented protections and remaining work

**DOCUMENTED:** `desktop/src-tauri/src/main.rs`, function
`write_json_with_recovery` (around line 848), uses a unique temporary file,
file `sync_all`, recovery copies and rename. The restore handler around
`desktop/ui/index.html:24455` saves an importable pre-restore snapshot before
separate library/draft/cue/localStorage writes, and compensates for normal errors.
As-run history write/ack is serialised and failures are retained until success
(`main.rs`, around line 5199). Claims that all of these protections are absent
would describe an earlier tree, not this release.

**INFERRED:** process termination between stores can leave a mixed station;
compensation cannot execute after termination. **COULD NOT ESTABLISH:** the
actual crash/power-loss outcomes on this release. SAVE-01 measures those before
choosing a journal/database redesign.

**DOCUMENTED defect:** the directory-open/sync results after rename in
`main.rs` (around lines 872 and 3445) are ignored. This can hide durability
uncertainty; no resulting data loss was measured. SAVE-02 must distinguish an
already committed file from uncertain power-loss durability, rather than adding
a misleading generic error after commit.

## LTC, MTC and physical acceptance

**DOCUMENTED:** `desktop/src-tauri/src/ltc.rs` explicitly limits codec evidence
to generated fixtures. Its tests cover measured-rate disagreement, damage and
inversion; the owner states LTC has not been tested. **COULD NOT ESTABLISH:**
independent real audio input/interface acceptance. LTC-01 remains open.

The input recovery path in `ltc_device.rs` (around line 691) catches selection
errors, chooses the default input and may clamp the channel. It reports the
substitution; calling it silent would be inaccurate. Enumeration reduced to a
count and closed-input polling limit named-device recovery (LTC-02).

Earlier MTC wire-encoding and generation/ownership defects have source repairs
and independent specification fixtures (`inter_app_midi.rs`, the MMA wire-example
test). Sender/receiver agreement is still not an independent receiver or timing
measurement. MTC-01, native permissions and long-show acceptance remain open.

## WING protocol and runtime

**DOCUMENTED:** Patrick-Gilles Maillot is the protocol authority. The local
pinned reference is acquired with [size and hash checks](PROTOCOL_REFERENCE.md),
not redistributed. Channel 3 request encoding and report-ID rejection are
implemented in `crates/wing-core/src/lib.rs` around lines 13130–13222. Group
normalisation belongs to `merge_descriptors` in the desktop backend (around
line 8838); the core encoder preserves the supplied order. The
backend renews every two seconds against the documented five-second timeout.

WING-01 must measure `0xA7`/`0xA8`, group lengths, `1/256 dB` and documented
exceptions, renewal, selected processing models, reconnect and cancellation on
controlled hardware. A request sent is not a confirmed resulting value.
Earlier overlap/cancellation/restore defects recorded in old release notes have
subsequent repairs; their physical acceptance remains distinct. No new live
console writes were made for this review.

## UI, security and dependencies

Matrix cells have button roles but no keyboard tab stop/navigation (around
`desktop/ui/index.html:30962`); UI-01 is an evidenced accessibility task.
Global Tauri exposure, inline CSP and window capabilities are a trust-boundary
review surface, not proof of an exploitable vulnerability (SEC-01).

**MEASURED:** npm's production-filtered lockfile audit reports **34 affected
package entries: 1 critical, 17 high, 14 moderate and 2 low**. These include parked
Expo/mobile and developer tooling; this count is not a desktop binary exploit
count. The critical shell-quote advisory is
[GHSA-pqg4-j6r4-53mv](https://github.com/advisories/GHSA-pqg4-j6r4-53mv).
DEP-01 requires reachability and supported updates, not an indiscriminate major
upgrade/downgrade of the parked mobile app.

The exact 292 external packages in the Apple Silicon desktop Cargo closure were
queried against OSV. Tokio 1.53.1 matched
[RUSTSEC-2026-0386](https://rustsec.org/advisories/RUSTSEC-2026-0386.html);
the release updates it to the patched 1.53.3 before verification. Five unic 0.9.0
entries have unmaintained-package notices, with no patched versions; track these
separately from the fixed Tokio advisory (DEP-02). Advisory queries are dated
snapshots, not proof of absence of undisclosed flaws.

## Publication and release checks

The release process must verify the complete source gate, arm64 architecture,
stable certificate/requirements, checksums, icon images, packaged legal notices
and matching source information. A self-signed certificate is **not** Apple
Developer ID signing or notarisation. The local install verifier clears
quarantine; its pass does not establish first-download approval on another Mac.

Secret-pattern scans, raw commit/tag identity checks and selected package
inspection reduce disclosure risk; no scanner proves every possible secret or
hidden binary datum absent. The private engineering history is excluded.
See the dated [validation record](VALIDATION.md) and release-specific notes for
actual results. A pending task is never closed by a generic green source gate.

## Decisions this audit takes

**D01 — Measure cross-store recovery before selecting a storage replacement.**
Grounds: implemented file protections and separate restore stores above.
Consequence: preserve existing recovery while gathering fault evidence.
Rejected alternative: replace storage with SQLite immediately; it would not
automatically transact browser localStorage and introduces migration risk.
What would overturn it: a measured failure and specified recovery contract that
justify a particular transactional design.

**D02 — Publish hardware/timecode work as open acceptance tasks.** Grounds:
the owner's LTC statement and explicit fixture-only evidence. Consequence:
contributors can supply reproducible reports without interpreting the release
as show certification. Rejected alternative: infer interoperability from unit
tests or prior general show use. What would overturn it: independent dated
hardware evidence covering the stated conditions and tolerances.

**D03 — Prioritise focused repairs and supported dependency changes.** Grounds:
the concrete audit surfaces above and stability-first product policy.
Consequence: no broad architecture rewrite or parked-mobile upgrade in a binary
release. Rejected alternative: apply every automated audit suggestion; npm
currently proposes an incompatible Expo downgrade. What would overturn it:
a demonstrated reachable defect requiring a broader supported migration.

## Documentation and presentation review — 9 November 2026

- Corrected `KNOWN_LIMITATIONS.md`'s obsolete statement that no installer was
  available: 0.3.0 is published, and later source/docs changes leave that binary
  unchanged.
- Added reproducible offline interface images, including channel selection,
  courtesy notices and HUD. These establish appearance only, not hardware
  behaviour. There is no testimonial or live-performance claim in the presentation.
- **UI-03 follow-up:** `desktop/ui/index.html:15399` formats a manual action-test
  notice with `macro.wingIp`; `:29146` describes the courtesy notice as firing
  before a trigger although the card is built from an activity report. These are
  text-hygiene/accuracy defects. Remove address/identity from operator notice
  text and correct its timing explanation in a focused UI change, with existing
  notice/browser contracts. Product media avoids that manual-test path.
- **UI-04 follow-up:** structured recipe detail at `desktop/ui/index.html:16860–16868`
  formats state/text triggers using the numeric meter threshold/unit. Correct it
  by parameter kind, with text/toggle/numeric/meter summary contracts. The public
  example uses a meter trigger, whose detail is accurate.
- **GUIDE-01 follow-up:** `docs/guide/02-triggers.md:116–117` overgeneralises gate
  expiry; meter staleness does not expire cached OSC state. Recipe 3 in
  `docs/guide/11-recipes.md:63–66` combines Level with Dwell although dwell affects
  rising transients only, and says fades never read despite current-value fades.
  Correct guide sources and their generated operator content together, checking
  behaviour against `main.rs:9634–9668` and `wing-runtime/src/lib.rs:304–357`.
- **GUIDE-01 additional evidence:** `docs/guide/04-macros-and-limits.md:39`
  incorrectly treats a fully empty trigger as incomplete; cue-only macros are
  accepted by `desktop/src-tauri/src/main.rs:10957–10973`. At
  `docs/guide/12-midi-and-other-applications.md:61–63`, Learn is said to capture
  a value range, but `inter_app_midi.rs:520–533` learns kind/channel/number and
  leaves value filtering deliberate. `docs/guide/02-triggers.md:126–128` says
  out-of-range meter IDs remain silent, while `crates/wing-core/src/lib.rs:4722–4729`
  drops them. Reconcile source and generated guide together in the guide repair.
- **Condition boundary, DOCUMENTED:** the macro IF list runs on meter and console
  state triggers (`main.rs:7524–7537`, `:9573–9582`). External bindings and cues
  reach `fire_macro` (`:3068–3124`), which executes the actions without evaluating
  that list. MIDI binding conditions separately watch tracked MIDI values
  (`inter_app_midi.rs:74–123`); OSC binding conditions compare an argument of the
  same message (`inter_app_osc.rs:317–329`). The product overview and sharing
  drafts now distinguish these paths. This is source evidence, not a newly
  measured hardware/integration result.

A presentation-draft lesson: the first draft inferred that the trigger itself was
single-channel from the grid picker. Source tests accept typed trigger lists
(`main.rs:19156–19169`); only the picker is single-selection. Both READMEs now
state that distinction. Another discarded draft set `delayMs` on a Set step;
Set ignores that field. Explicit Wait / Wait then Set modes are the supported
representations. Neither discarded draft was published as a show preset.

## Community reporting — 9 November 2026

The public README and installation guides now link to native GitHub forms for
bugs, improvements, defined tests and use experiences. Intake labels classify
reports; outcome labels are applied manually after review. A user report does
not certify another setup. `COMMUNITY_TESTING.md` defines scope, evidence and
triage; the disclaimer now names incomplete beta validation across hardware,
integrations and failure paths.

The owner explicitly removed the maintainer testimonial and the untested named
application recommendation from the product presentation and sharing drafts.
The introduction now includes LTC/MTC cues alongside meter/state and inter-app
MIDI/OSC triggers. These edits change documentation, not the released binary.
